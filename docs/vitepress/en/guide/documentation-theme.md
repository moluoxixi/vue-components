# Documentation Theme and Reuse

The documentation site uses the standalone `@moluoxixi/vitepress-theme-element-plus` package for its complete Element Plus-style VitePress theme. The package builds on VitePress's stable layout runtime and owns navigation, sidebars, mobile menus, page outlines, dark mode, document pagination, NotFound behavior, and reusable Demo, Playground, and ApiDocs content runtime. The component library keeps only its site configuration, component catalog, prose, examples, and project data.

## Adopt it in another component library

1. Install the theme package and import `defineElementPlusDocs` from its root entry. Keep one configuration object in `.vitepress/config.ts` for the brand, logo, consumer styles, repository, public routes, and locales.
2. Export `elementPlusDocsTheme` directly from `.vitepress/theme/index.ts`. When the site must register local components or Vue plugins, use `createElementPlusDocsTheme({ enhanceApp })` from the same root entry. The theme entry and the configuration factory from step one must be used together so consumer styles can be injected.
3. Maintain the target library's component catalog and content in the consumer. Register `Demo`, `Playground`, `ApiDocs`, and catalog content through `createElementPlusDocsContent`, then enable the Demo container with `@moluoxixi/vitepress-theme-element-plus/markdown`. The consumer supplies only allowed runtime modules, starter source, generated API JSON, and project metadata; repository-metadata synchronization and API extraction remain consumer-owned.
4. Declare each locale's language tag, VitePress site key, and URL prefix separately. For example, Chinese can use `zh-CN`, `root`, and an empty prefix while English uses `en-US`, `en`, and `/en`; the theme does not infer routes from language tags.
5. Run the theme package type check, tests, build, and neutral fixture build before running the target documentation site's tests and production build.

Repository metadata is supplied by a registry-backed provider model. The site registers `github`, `local`, `gitlab`, `gitee`, and `yunxiao`, and strictly selects one through `docsSite.metadataProvider`; production remains configured for `github`. The theme package exports the platform-neutral metadata contract, registry, capability filtering, content adapter, and platform URL actions. Credentials, API clients, synchronization commands, validators, and generated snapshots remain site-owned. There is no `auto` mode, file fallback, or cross-provider merge, and an unknown provider fails before snapshot loading. API contracts, provider snapshots, and generated declarations live only under the Git-ignored `.generated/{api,repository,types}` root instead of beside `.vitepress` source.

Local debugging can select a provider at startup through `VITE_DOCS_REPOSITORY_METADATA_PROVIDER` without editing source. For example, use `$env:VITE_DOCS_REPOSITORY_METADATA_PROVIDER='gitlab'; pnpm -C docs/vitepress dev` in PowerShell or `VITE_DOCS_REPOSITORY_METADATA_PROVIDER=gitlab pnpm -C docs/vitepress dev` in a POSIX shell. A missing or blank value still selects `github`; an unsupported value fails instead of falling back to another snapshot. This is a build-time selector, not an in-browser runtime switch.

Each provider has explicit `sync-*-metadata` and `validate-*-metadata` commands targeting `.generated/repository/<provider>.json`. Supported `pnpm -C docs/vitepress dev` and `build` commands first run one prepare pipeline that builds workspace dependencies, generates routes, extracts API contracts, then synchronizes and validates the selected provider. Every milestone emits `[docs:prepare] START / OK / FAIL` with its name, duration, provider, output directory, and failure code. Deterministic synthetic fixtures cover all five provider schemas, normalizers, capabilities, and selection without production snapshots or external services; required CI contacts only the default GitHub provider during the production docs build using the workflow token, never GitLab, Gitee, or Yunxiao. GitLab supports explicit web/API roots, relative installation paths, and full subgroup project paths. Private projects use runtime-only `GITLAB_TOKEN` credentials with either `PRIVATE-TOKEN` or Bearer authentication. Trusted CAs and proxies for self-signed installations are configured in the Node runtime environment; the collector does not bypass TLS validation. Gitee uses public-cloud REST v5 as its tested baseline; web/API roots are configurable, but enterprise installations require instance-specific verification, with optional `GITEE_TOKEN`. Markdown demo sources use `/blame/...#Lx` to locate the exact start line. A Gitee commit API account ID/login must exactly match the user API result for that same login; another Gitee account is never treated as an alias. Yunxiao represents both central and regional tenant API shapes and requires a runtime-only `YUNXIAO_TOKEN` with repository, commit, branch, and member read-only permissions. Codeup commit names and emails derive privacy-safe mapping keys only; `contributorAccounts` explicitly selects each reviewed exact online username. The same repository's `/members` API must return exactly one active matching account and supplies the current login, name, and trusted avatar reused by contributor cards and changelog entries. Missing mappings, zero or ambiguous member lookups, partial/conflicting account fields, or unsafe/off-provider avatars abort synchronization and preserve the previous snapshot instead of inferring an account from email or falling back to configured profiles or initials. Component-directory, file, and single-line anchor routes have been verified against the real Codeup fixture. Because non-README Markdown opens in a preview without line numbers, the theme adds Codeup's `README.md` source-view compatibility parameter to Markdown demo links before applying the `#Lx` anchor. Issues, online editing, and unverified contributor profile links remain disabled. Collectors never serialize author email or tokens, and pagination cannot escape the configured API origin and path prefix.

GitLab component commits are the sole contribution-history source, and per-component contribution counts are derived from commits under each component path. Commit names and emails are used only to derive a privacy-safe `gitlab:<sha256>` identity and are never used to guess an account. Synchronize once to obtain that ID, review an exact GitLab username, and add the pair to `contributorProfiles`. The next synchronization must resolve exactly one matching account through `GET /users?username=` and apply its complete login, name, avatar, and profile URL atomically to the contributor and every matching commit author. A missing mapping, zero or ambiguous lookup, username mismatch, unavailable endpoint, cross-instance URL, authentication error, network error, pagination error, or malformed payload aborts synchronization and preserves the previous snapshot; there is no initials or cross-source fallback. Mappings, snapshots, and logs never store email addresses. GitLab versions may return either `/-/issues/:iid` or `/-/work_items/:iid`; both are validated. Issue data and actions are disabled when Issues are unavailable, while project-level authentication failures still fail synchronization.

Provider capabilities are maximums and snapshots may only disable them. GitLab and Gitee hide both Issue data and actions when a project disables Issues. Yunxiao has no repository-level Issues, so `issues` and `issueActions` are always disabled. Its `sourceLinks` capability uses the real-tenant-verified `/tree` and `/blob` routes; Markdown links activate Codeup's source view before `#Lx` locates the start of each demo. `editLinks` remains disabled; Projex work items and Codeup change requests are never presented as repository Issues.

The Husky `pre-commit` hook never generates, refreshes, or stages metadata. Ignored snapshots are produced only by docs dev/build preparation or an explicit `sync-*-metadata` command. GitHub Actions and Pages synchronize GitHub in the docs build step with a minimal read-only workflow token; npm package builds and publishing never trigger documentation metadata synchronization. Selecting a source-management provider does not create GitLab CI, Gitee Go, or Yunxiao Flow deployment configuration.

API names, types, and descriptions remain owned by the extracted source contract instead of being duplicated in Markdown. Theme controls and generated page shells are fully bilingual. Locale source documents and source JSDoc can be translated incrementally by component authors.

## Maintenance boundary

The theme package is the single source of truth for layout, Element Plus installation, base styles, Demo/Playground/ApiDocs runtime, and shared interactions. Consumers own site identity, component content, and project data. Version one is a fixed copy of a recorded Element Plus documentation-theme commit; subsequent changes are maintained in the standalone package without automatic upstream tracking or per-site theme copies.
