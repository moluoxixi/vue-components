# Documentation Theme and Reuse

The documentation site uses the standalone `@moluoxixi/vitepress-theme-element-plus` package for its complete Element Plus-style VitePress theme. The package builds on VitePress's stable layout runtime and owns navigation, sidebars, mobile menus, page outlines, dark mode, document pagination, NotFound behavior, and reusable Demo, Playground, and ApiDocs content runtime. The component library keeps only its site configuration, component catalog, prose, examples, and project data.

## Adopt it in another component library

1. Install the theme package and import `defineElementPlusDocs` from its root entry. Keep one configuration object in `.vitepress/config.ts` for the brand, logo, consumer styles, repository, public routes, and locales.
2. Export `elementPlusDocsTheme` directly from `.vitepress/theme/index.ts`. When the site must register local components or Vue plugins, use `createElementPlusDocsTheme({ enhanceApp })` from the same root entry. The theme entry and the configuration factory from step one must be used together so consumer styles can be injected.
3. Maintain the target library's component catalog and content in the consumer. Register `Demo`, `Playground`, `ApiDocs`, and catalog content through `createElementPlusDocsContent`, then enable the Demo container with `@moluoxixi/vitepress-theme-element-plus/markdown`. The consumer supplies only allowed runtime modules, starter source, generated API JSON, and project metadata; repository-metadata synchronization and API extraction remain consumer-owned.
4. Declare each locale's language tag, VitePress site key, and URL prefix separately. For example, Chinese can use `zh-CN`, `root`, and an empty prefix while English uses `en-US`, `en`, and `/en`; the theme does not infer routes from language tags.
5. Run the theme package type check, tests, build, and neutral fixture build before running the target documentation site's tests and production build.

Repository metadata is supplied by a registry-backed provider model. The site registers `github`, `local`, `gitlab`, `gitee`, and `yunxiao`, and strictly selects one through `docsSite.metadataProvider`; production remains configured for `github`. The theme package exports the platform-neutral metadata contract, registry, capability filtering, and platform URL actions. Credentials, API clients, synchronization commands, validators, and independent JSON snapshots remain site-owned. There is no `auto` mode, file fallback, or cross-provider merge, and an unknown provider fails before snapshot loading. Normal `dev` and `build` validate and consume only the selected snapshot without platform API access.

Local debugging can select a provider at startup through `VITE_DOCS_REPOSITORY_METADATA_PROVIDER` without editing source. For example, use `$env:VITE_DOCS_REPOSITORY_METADATA_PROVIDER='gitlab'; pnpm -C docs/vitepress dev` in PowerShell or `VITE_DOCS_REPOSITORY_METADATA_PROVIDER=gitlab pnpm -C docs/vitepress dev` in a POSIX shell. A missing or blank value still selects `github`; an unsupported value fails instead of falling back to another snapshot. This is a build-time selector, not an in-browser runtime switch.

Each provider has explicit `sync-*-metadata` and offline `validate-*-metadata` commands. `validate-repository-metadata` is CI's offline aggregate and validates GitHub, GitLab, Gitee, local, and the real Yunxiao snapshot; it never performs network synchronization. GitLab supports explicit web/API roots, relative installation paths, and full subgroup project paths. Private projects use runtime-only `GITLAB_TOKEN` credentials with either `PRIVATE-TOKEN` or Bearer authentication. Trusted CAs and proxies for self-signed installations are configured in the Node runtime environment; the collector does not bypass TLS validation. Gitee uses public-cloud REST v5 as its tested baseline; web/API roots are configurable, but enterprise installations require instance-specific verification, with optional `GITEE_TOKEN`. Yunxiao represents both central and regional tenant API shapes and requires `YUNXIAO_TOKEN` for live synchronization. The tracked snapshot has been synchronized and validated against a retained private Codeup fixture through the central API, including repository identity, default branch, component commits, and contributor aggregation. Yunxiao currently exposes commit history and contributor data only; Issues, source, edit, line, and contributor-profile links remain disabled until their real routes are independently verified. Collectors never serialize author email or tokens, and pagination cannot escape the configured API origin and path prefix.

GitLab synchronization first requests the project's `/repository/contributors` online contributor endpoint, while component-level contribution counts continue to come from commits for each component path. It falls back to commit scanning only when the installation explicitly returns 404/405 because that endpoint is unavailable; 401/403 responses, network errors, and malformed payloads fail synchronization. The endpoint does not expose a verifiable account relationship, so contributor accounts are never guessed from commit names or email addresses. Synchronize once to obtain the privacy-safe `gitlab:<sha256>` contributor ID, review an exact GitLab username, and add that pair to `contributorProfiles`. The next synchronization performs an exact `GET /users?username=` lookup and adds the login, avatar, and profile URL only when the response is unambiguous and stays inside the configured instance. Missing, ambiguous, mismatched, unavailable, or cross-origin results keep the per-contributor initials fallback. Mappings, snapshots, and logs never store email addresses. GitLab versions may return either `/-/issues/:iid` or `/-/work_items/:iid`; both are validated. Issue data and actions are disabled when Issues are unavailable, while project-level authentication failures still fail synchronization.

Provider capabilities are maximums and snapshots may only disable them. GitLab and Gitee hide both Issue data and actions when a project disables Issues. Yunxiao has no repository-level Issues, so `issues` and `issueActions` are always disabled. Its source, line-anchor, and edit actions also remain disabled until exact routes are proven in a real tenant; Projex work items and Codeup change requests are never presented as repository Issues.

The existing Husky `pre-commit` hook refreshes and stages only `.vitepress/local-metadata.json`. Network providers do not run in the commit hook, so commits do not depend on platform availability, tokens, or rate limits. The scanner resolves the configured default branch rather than an arbitrary checked-out `HEAD`. A pending commit SHA does not exist until after the hook completes, so a commit made on the default branch covers history through that branch's pre-commit head; the newly created commit appears on the next refresh. GitHub Actions/Pages and npm publishing remain owned by the existing GitHub workflows; selecting a source-management provider does not create GitLab CI, Gitee Go, or Yunxiao Flow deployment configuration.

API names, types, and descriptions remain owned by the extracted source contract instead of being duplicated in Markdown. Theme controls and generated page shells are fully bilingual. Locale source documents and source JSDoc can be translated incrementally by component authors.

## Maintenance boundary

The theme package is the single source of truth for layout, Element Plus installation, base styles, Demo/Playground/ApiDocs runtime, and shared interactions. Consumers own site identity, component content, and project data. Version one is a fixed copy of a recorded Element Plus documentation-theme commit; subsequent changes are maintained in the standalone package without automatic upstream tracking or per-site theme copies.
