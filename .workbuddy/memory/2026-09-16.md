## e2e 对齐续：修掉 3 个真实产品缺陷（均经定向跑验证/定位）

起点：上一轮全量 121 项 / 111 通过 / 10 失败。本轮不满足于"改测试断言去凑绿"，先把失败背后的产品缺陷挖干净，用定向 `--grep` 单跑（15–40s）做反馈循环。

### 缺陷 1（已修 + 已验证）：空文本字面量被 Vue 布尔转换吃掉

- 现象：`compare` 条件右操作数模型是 `{ kind: 'literal', value: '' }`，但 UI 渲染成 **Value type = Boolean + 开关**，没有文本输入框 → `operands.nth(1).getByRole('textbox')` 必然超时（nested branches 2 项挂在这）。
- 定位证据链（可复用）：
  1. 给 `OperandEditor` / `ValueEditor` 临时挂 `data-probe-*` 属性把 props 打到 DOM：父组件 `modelValue` = `{"kind":"literal","value":""}`，而子组件 `ValueEditor` 收到的是**布尔 `true`**（`rawType: "boolean"`）。
  2. 用 `getCurrentInstance().propsOptions[0].modelValue` 读出**归一化后的 prop 选项**：`{ shouldCast: true, shouldCastTrue: true, type: [Boolean, null, Number, String, Object, Array] }`。
  3. 对照 `@vue/runtime-core` 的 `resolvePropValue` / `normalizePropsOptions`：数组型 `type` 遇到 `Boolean` 即 `shouldCast = true` 并 break；`String` 排在 `Boolean` **之后**，所以 `shouldCastTrue` 保持 `true` → `value === ''` 被改写成 `true`。
- 结论：`ConfigFormValueInput` 的联合类型被推断成 **Boolean 在前、String 在后**，于是**任何**消费者只要传 `''` 都会被转成 `true`（`OperandEditor` 因为默认值显式用 `''` 才踩到；`ActionInputs` 的默认值是 `undefined` 所以没踩）。
- 修复（`OperandEditor/index.vue`）：在传给 `ValueEditor` 的边界上把 `''` 归一化为 `undefined`（`literalEditorValue` computed）。语义等价（空串与未设置都渲染同一个空文本框），模型不动。**未动核心类型**，避免 core 重编译风险。
- 遗留：`ValueEditor.modelValue` 这个 footgun 仍在。真正根治要么让 prop 类型 String 在前、要么显式声明运行时 prop；要单独排期（会影响所有传 `''` 的调用点）。

### 缺陷 2（已修 + 已验证）：Step label 无法输入

- 现象：`fill()` 之后立刻读 `inputValue()` 就是 `''`；树标签永远是回退标题（Condition / Delay / success…）。
- 根因：`FlowWorkspace/index.vue` 的 `<ElInput :model-value="selectedStep.title ?? ''" @change="updateTitle" />` **只绑了 `:model-value` 没接 `@update:model-value`**。Element Plus 的 `ElInput` 在 `handleInput` 里会 `await nextTick(); setNativeInputValue()`，模型没更新就把 DOM 值**弹回** `props.modelValue`，所以永远打不进字。
- 修复：加本地草稿 `stepTitleDraft`（`@update:model-value` 写草稿，`@change` 提交 trim 后的标题，并 watch `[selectedStep.id, selectedStep.title]` 回灌）。不能用"改成 `@update:model-value="updateTitle"`"的偷懒写法：`updateTitle` 会 trim，逐键提交会把输入中的空格立刻吃掉（"Name gate" 会变 "Namegate"）。
- 验证：nested branches 的树标签断言（`.flow-step-label strong` → 7 个自定义标题）**已通过**；component event flow 2 项从 1219 行推进到 1228 行。

### 缺陷 3（已定位，未修）：步骤标题把 edge id 撑爆 128 上限

- 现象：修好缺陷 2 后，nested branches 卡在 `saveFlow()` —— 弹窗不关闭，`.flow-diagnostics` 显示 `PROJECT_FLOW_INVALID` / `Flow is invalid. String must contain at most 128 character(s)`（诊断**没有 path**，只能靠算）。
- 根因：`core/src/flow-authoring/services/conversion.ts:106` 把**目标步骤标题按每字符 4 个十六进制位**编进每条边的 id（`edge.id += encodeEdgeTitle(title)`，`encodeEdgeTitle` 见 921-928 行）；而边 id 本身已经是 `$flow-authoring:edge:${source.length}:${source}:${condition}`，其中 join 节点 id 长 42（`$flow-authoring:join:18:flow-1-condition-1`）。于是「join 边 → 有标题目标」的 id 长度 = **78 + 4×标题长度**；`Submit allowed`（14 字符）→ 134 > 模型 `identifierSchema.max(128)`（`model/src/schemas/project.ts:61`，被 `flowSchema` 的 edges/nodes 复用）→ 校验失败 → 无法保存。
- 这个缺陷此前被缺陷 2 **掩盖**：标题永远不落库 → 编码都是 `:title:n`（8 字符）→ 不会超限。**修好缺陷 2 就必然暴露它。**
- 可选修法（需决策，别单方面改 core 契约）：① 标题改用更紧凑的编码（base64url ≈1.33 字符/字符，保留旧 hex 解码兼容），能把上限从 ~13 字符标题提到 ~35；② 边 id 不再内嵌 `source`（省 ~45 字符）；③ 把标题从 id 里搬走（`readEdgeTitles` 依赖 id 自描述，要改 schema）；④ 放宽 edge id 的 max（属于契约变更）。②+① 组合后余量最大。
- 相关：`getJoinId`（900 行）同理把 condition id 内嵌，长 id 的导入工程也有同类风险。

## 架构审计：runtime 与 designer 的隔离程度（结论：物理隔离成立，概念隔离不成立）

用户提问「configform 是不是集成了很多设计器的内容，二者架构未能隔离」。核查结论：

**做对的部分（有实测证据）**
