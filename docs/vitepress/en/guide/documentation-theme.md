# Documentation Theme and Reuse

The documentation site uses the standalone `@moluoxixi/vitepress-theme-element-plus` package for its complete Element Plus-style VitePress theme. The package builds on VitePress's stable layout runtime and owns navigation, sidebars, mobile menus, page outlines, dark mode, document pagination, NotFound behavior, and reusable Demo, Playground, and ApiDocs content runtime. The component library keeps only its site configuration, component catalog, prose, examples, and project data.

## Adopt it in another component library

1. Install `@moluoxixi/vitepress-theme-element-plus` and create one `element-plus-docs.config.ts` at the documentation root. Use `defineElementPlusDocsProject` for the repository, documentation locales, package profiles, and component catalog. Package profiles derive API entries, documentation paths, repository paths, runtime modules, and styles.
2. Use `defineElementPlusDocs` in `.vitepress/config.ts` for branding, public routes, and locales. Export `elementPlusDocsTheme`, or use `createElementPlusDocsTheme({ enhanceApp })` for site-specific plugins.
3. Register Demo, Playground, ApiDocs, and catalog content with `createElementPlusDocsContent`, then install `elementPlusDocsProjectMarkdownPlugin`. The theme generates precise source-line links and the minimal subpaths, dependencies, and styles required by CodeSandbox/StackBlitz; consumers do not implement resolver callbacks.
4. Wire package scripts to `element-plus-docs dev`, `element-plus-docs build`, and `element-plus-docs prepare`. The CLI loads the same project configuration, synchronizes and validates the selected snapshot, then starts or builds VitePress.
5. Declare language tags, VitePress site keys, URL prefixes, content directories, and authoring source documents under `documentation.locales`. A package profile that needs minimal-subpath Playground projects uses `loadPlaygroundManifest: () => import('<package>/playground-manifest')`. The CLI builds workspace dependencies before invoking this loader, so do not statically import a not-yet-generated manifest at config load time.

The theme package includes `github`, `local`, `gitlab`, `gitee`, and `yunxiao`. A normal consumer configures only `repository: { provider, url }`: GitHub and Gitee derive owner/repository, GitLab derives project and installation coordinates, local derives the Git root/remote/default branch, and Yunxiao additionally requires its non-derivable `repositoryId`. Configure `repositoryProviders` only when one site intentionally supports debug switching. There is no `auto`, local fallback, file fallback, or cross-provider merge. API contracts, repository snapshots, Playground manifest snapshots, and declarations live only under the ignored `.generated/{api,repository,markdown,types}` root.

Local debugging can select a provider at startup through `VITE_DOCS_REPOSITORY_METADATA_PROVIDER` without editing source. For example, use `$env:VITE_DOCS_REPOSITORY_METADATA_PROVIDER='gitlab'; pnpm -C docs/vitepress dev` in PowerShell or `VITE_DOCS_REPOSITORY_METADATA_PROVIDER=gitlab pnpm -C docs/vitepress dev` in a POSIX shell. A missing or blank value selects `repository.provider` from `element-plus-docs.config.ts` (GitHub in this project); an unsupported value fails instead of falling back. This is a build-time selector, not an in-browser runtime switch.

`element-plus-docs prepare` is the single synchronization and validation entry; `dev` and `build` run it automatically. Every milestone emits `[docs:prepare] START / OK / FAIL` with its name, duration, provider, output path, and exit code, while an exclusive lock prevents concurrent preparation. The CLI dynamically loads only the selected collector and reads only its `GITHUB_TOKEN`, `GITLAB_TOKEN`, `GITEE_TOKEN`, or `YUNXIAO_TOKEN`. Theme-owned synthetic fixtures test all five schemas, normalizers, capabilities, and selection offline; required CI contacts only production's selected GitHub provider.

GitLab supports explicit web/API roots, installation subpaths, and subgroups, with runtime `GITLAB_TOKEN` authentication. Gitee defaults to public-cloud REST v5, supports optional `GITEE_TOKEN`, and uses `/blame/...#Lx` for Markdown demos. Yunxiao requires a read-only `YUNXIAO_TOKEN` for repository, commit, branch, and member APIs. GitLab and Yunxiao commit identities produce privacy-safe mapping keys only; `contributorProfiles` or `contributorAccounts` must map them to reviewed exact online accounts. Authentication, network, mapping, pagination, URL-trust, or payload failures abort synchronization and preserve the previous snapshot byte-for-byte.

GitLab component commits are the sole contribution-history source, and per-component contribution counts are derived from commits under each component path. Commit names and emails are used only to derive a privacy-safe `gitlab:<sha256>` identity and are never used to guess an account. Synchronize once to obtain that ID, review an exact GitLab username, and add the pair to `contributorProfiles`. The next synchronization must resolve exactly one matching account through `GET /users?username=` and apply its complete login, name, avatar, and profile URL atomically to the contributor and every matching commit author. A missing mapping, zero or ambiguous lookup, username mismatch, unavailable endpoint, cross-instance URL, authentication error, network error, pagination error, or malformed payload aborts synchronization and preserves the previous snapshot; there is no initials or cross-source fallback. Mappings, snapshots, and logs never store email addresses. GitLab versions may return either `/-/issues/:iid` or `/-/work_items/:iid`; both are validated. Issue data and actions are disabled when Issues are unavailable, while project-level authentication failures still fail synchronization.

Provider capabilities are maximums and snapshots may only disable them. GitLab and Gitee hide both Issue data and actions when a project disables Issues. Yunxiao has no repository-level Issues, so `issues` and `issueActions` are always disabled. Its `sourceLinks` capability uses the real-tenant-verified `/tree` and `/blob` routes; Markdown links activate Codeup's source view before `#Lx` locates the start of each demo. `editLinks` remains disabled; Projex work items and Codeup change requests are never presented as repository Issues.

The Husky `pre-commit` hook never generates, refreshes, or stages metadata. Ignored snapshots are produced only by `element-plus-docs prepare/dev/build`. GitHub Actions and Pages synchronize GitHub in the docs build step with a minimal read-only workflow token; npm package builds and publishing never trigger documentation metadata synchronization. Selecting a provider does not create GitLab CI, Gitee Go, or Yunxiao Flow deployment configuration.

API names, types, and descriptions remain owned by the extracted source contract instead of being duplicated in Markdown. Theme controls and generated page shells are fully bilingual. Locale source documents and source JSDoc can be translated incrementally by component authors.

## Maintenance boundary

The theme package is the single source of truth for layout, Element Plus installation, base styles, Demo/Playground/ApiDocs runtime, and shared interactions. Consumers own site identity, component content, and project data. Version one is a fixed copy of a recorded Element Plus documentation-theme commit; subsequent changes are maintained in the standalone package without automatic upstream tracking or per-site theme copies.
