# Type Safety

> Type contracts for public frontend tooling APIs.

## Overview

Public configuration factories must express scenario-specific fields in their
input types. Shared helpers accept only their common option surface, and
deprecated public interfaces retain their declaration shape during compatibility
transitions.

## Scenario: Separate Application and Library Vite Configuration

### 1. Scope / Trigger

- Trigger: changing a public Vite configuration factory or its option types.
- Applies to `createAppConfig`, `createLibConfig`, `getBaseConfig`, addon
  inspection, addon registration, and library dependency externalization.

### 2. Signatures

```ts
interface BaseViteConfigOptions {
  viteConfig?: UserConfig
  // Typed automatic addon options.
}

interface LibViteConfigOptions extends BaseViteConfigOptions {
  entry?: LibraryOptions['entry']
}

interface AppViteConfigOptions extends BaseViteConfigOptions {
  appName?: string
  appCode?: string
}

function createAppConfig(config?: AppViteConfigExport): UserConfigExport
function createLibConfig(config?: LibViteConfigExport): UserConfigExport
function getBaseConfig(options?: BaseViteConfigOptions): Promise<UserConfig>
```

Deprecated public interfaces remain interfaces when declaration merging may be
used by consumers:

```ts
/** @deprecated Use AppViteConfigOptions or LibViteConfigOptions. */
interface ViteConfigOptions extends LibViteConfigOptions {}
```

### 3. Contracts

- Application-only factories must not accept `entry`; Library factories must
  not accept application identity fields.
- Shared addon helpers accept `BaseViteConfigOptions`; scenario-only fields are
  never silently ignored.
- Business-owned plugins, including Sentry, are installed and configured by the
  consumer through `viteConfig.plugins`. They are not automatic addons or
  optional peers of the preset package.
- Library builds automatically externalize dependencies, optional dependencies,
  peer dependencies, and their subpaths.
- Caller `build.rollupOptions.external` rules are combined with the automatic
  dependency rule using logical OR.
- Library dependency externalization is invariant and cannot be disabled.
- `appCode` supplies the default application base; `appName` / `appCode` are
  exposed as `__APP_NAME__` / `__APP_CODE__`, with raw user config winning.
- `pages` uses the native `vite-plugin-pages` options. Its defaults are
  `dirs: 'src/pages'`, `exclude: ['**/components/**', '**/__tests__/**']`, and
  `.vue` extensions for Vue projects; pure React projects use `resolver:
  'react'` and `.tsx` extensions.
- `html` uses the native `vite-plugin-html` options and calls its named
  `createHtmlPlugin` export. It does not invent template, entry, or injection
  defaults.

### 4. Validation & Error Matrix

| Condition | Required Result |
|---|---|
| `createAppConfig({ entry })` | Compile-time error |
| `getBaseConfig({ appCode: 'demo' })` | Compile-time error |
| Library dependency subpath | Final external predicate returns `true` |
| Caller external string, RegExp, array, or predicate matches | Final predicate returns `true` |
| `createLibConfig({ appCode: 'demo' })` | Compile-time error |
| Declared `vite-plugin-pages` or `vite-plugin-html` | Feature inspection enables the matching addon |
| Enabled pages/html dependency missing at runtime | Error names the addon and missing package |
| Required addon dependency missing | Runtime error names the addon, package, and project root |

### 5. Good / Base / Bad Cases

- Good: `createLibConfig({ entry: 'src/index.ts' })`.
- Base: `createAppConfig({ appCode: 'demo', appName: 'Demo App' })`.
- Good: `createAppConfig({ pages: { dirs: 'src/pages' }, html: { verbose: true } })`.
- Bad: adding business credentials, organization IDs, release rules, or Sentry
  environment conventions to the automatic addon registry.
- Bad: replacing automatic dependency externalization merely because the caller
  supplied another Rollup external rule.

### 6. Tests Required

- Type tests reject Library-only fields for application and shared helpers.
- Type tests prove deprecated public interfaces still support module
  augmentation.
- Unit tests cover caller external strings, regular expressions, arrays, and
  predicates while asserting automatic dependency and subpath matches remain.
- Unit tests assert app identity defaults and explicit user overrides.
- Unit tests assert Vue/React pages defaults and `createHtmlPlugin` named export
  loading; inspection tests cover automatic dependency detection.
- Build and declaration generation must export all new public option types.

### 7. Wrong vs Correct

#### Wrong

```ts
type ViteConfigOptions = LibViteConfigOptions // Breaks interface augmentation.

return mergeConfig(defaultLibraryConfig, {
  build: { rollupOptions: { external: userExternal } },
}) // Silently replaces dependency externalization.
```

#### Correct

```ts
interface ViteConfigOptions extends LibViteConfigOptions {}

const external = (id: string, importer?: string, isResolved?: boolean) =>
  dependencyExternal(id) || matchesUserExternal(userExternal, id, importer, isResolved)

const { createHtmlPlugin } = await ctx.importRequired('html', 'vite-plugin-html')
return { plugins: createHtmlPlugin(options) }
```
