### 设计画布空白 bug（用户报障后修复）

- 根因：`DesignRuntimeHostFrame` 发出的 `sync`/`state` 载荷缺 `runtimeState.fields`，而子框架的入站守卫 `isRuntimeHostParentMessage`（经 `isRuntimeHostRuntimeState`）要求该字段必须是数组 → 子框架静默忽略所有 sync → 画布只有一个 1px 高的空 iframe。
- 定位手法（可复用）：画布 iframe 内联高度 + 子框架 `data-mode`/`data-runtime-session` 作为状态探针；用 `addInitScript` 在父子两个 realm 同时打点 `postMessage` 与 `message`；在子框架内**动态 import 协议守卫**并喂真实载荷，把「猜」变成布尔判定。
- 修复：新增 `designRuntimeState(): RuntimeHostRuntimeStatePayload` 显式返回 `fields: []`，并给载荷加返回类型标注（原先直接传字面量给 `postMessage(Record<string, unknown>)`，缺字段无法被类型检查发现）。
- 并修握手健壮性：sync 未获子框架确认前每 400ms 重发（上限 25 次），避免消息落在子框架监听器挂载之前而永久丢失。
- 验证：画布渲染出 Name/Role/Active，iframe 高度 1px → 74px，`data-mode="design"`。
- 注意：本仓库 `runtime-host` 协议对 `runtimeState.fields` 是硬性要求，任何父级→子级载荷构造都要走类型化构造器。

### 环境/流程经验（本项目专属）

- `pnpm exec <bin>` 在本机不可用；用包脚本（`pnpm --filter <pkg> test`、`pnpm --dir <pkg> typecheck`）。
- Headless/Core/Runtime 的**跨包 typecheck 与 build 依赖 dist**：改动 core/headless 后必须先 `build`，否则下游读到过期 `.d.ts`（曾导致 10 处「属性不存在」假故障）。Runtime build 失败会清空 dist，风险较高。
- `pnpm typecheck`（turbo）被循环依赖阻塞，只能逐包跑。
- vitest 会调用 `wmic.exe` 被安全策略拦截，命令输出可能被替换，但产物仍会写出；用「写文件 + 读取」而非依赖 stdout。
- 全量工作台套件在高负载下会把 5s 边界用例（`data-workspace`）顶超时：单 worker 会减少失败数但不会消失，属预算临界而非逻辑错误。
- e2e（playwright + `pnpm dev`）在本机无法跑通：设计画布 iframe 的模块请求全部 `ERR_ABORTED`，子框架永不初始化；`createProject()` 因此必然失败。

## 架构评审：新版 ConfigForm vs 旧版 `oldVueComponent/packages/components/ConfigForm`

结论：新版在架构、类型安全、可测试性上全面更优，差距是工程级的而非风格偏好。

- 旧版问题（证据）：`src/index.vue`（script setup）与 `src/starfish-form.vue`（Options API）是同一份 330 行实现的近乎重复；两文件各含 4 处 `eval()`；`_types/props.ts` 三个 prop 全是 `any[]` / `Record<string, any>`；`getRules` 用硬编码 `ControlType === 'Grid' / 'TableLayout' / 'Collapse' / 'Tabs'` 分支递归；`handleControlChange` 就地 mutate `props.allFormList[].show`；`executeFunc` 里 `forEach` 返回值被丢弃 → action 永远拿不到（真 bug）；`layout/grid.vue` 残留 `console.log(props)`，并用字符串 key `inject('control')` 把设计器 store 与运行时渲染混在一起；整个 ConfigForm 目录 0 个测试；README 把 `any` 描述成「完整的 TypeScript 类型支持」。
- 新版优势（证据）：`packages/ConfigForm` 下单包独立发布（core / model / compiler / headless / runtime / element / antd / designer(+2 adapter) / workbench / plugin-* / vue-backend / devtools），顶层 `README.md` 给出 mermaid 依赖图和「禁止依赖」清单；`architecture-boundary.test.ts` 在 model/compiler/designer/workbench/vue-backend 中机械校验目录形态与非法 import；`headless/src/types/props.ts` 与 `controller.ts` 用泛型 `TValues extends ConfigFormValues` 全链路打通；src 下 `eval` 0 处、`: any` 近乎 0；170+ 测试文件含 architecture-boundary / production-performance / business-scenarios-parity；每个子包带 README + CHANGELOG。
- 新版待改进：`headless/src/services/controller.ts` 有效代码 1186 行、单函数闭包内约 40 个内部函数，是唯一明显的可读性瓶颈，建议按 values / validation / rows / lifecycle 拆成对象组合；`as unknown as TValues` 在 controller 与 scope 层多次出现，是泛型与 JSON 值域模型的边界妥协；值域类型名很长（如 `ConfigFormValueScopeRowMutationResult`），新人上手成本高于旧的 `item.data.xxx`。
- 提醒：新旧不是同量级系统（旧版是耦合 FormDesign store 的单个组件，新版是含设计器/工作台的平台），「旧版单文件更短」是因为复杂度被藏进了 magic string 分支与静默 catch。

## 决策：不建议把新版 ConfigForm 改成 class 化

用户问「新版有没有必要改成 class 之类的」。结论：不整体改。已实测两条关键证据（用 `node_modules/.pnpm/typescript@5.9.3` 的 tsc + node 24 跑，临时目录已删除）：

- `tsc --strict --target ESNext --noEmit` 对「带原型方法的类实例赋给函数类型属性接口（`getErrors: () => string`）+ 解构该方法」**零报错，exit=0** → 类型系统拦不住 `this` 丢失。
- 运行时实测：类实例解构出的方法调用抛 `TypeError: Cannot read properties of undefined`；同结构的工厂闭包版本正常返回。

因此 class 化会静默打断这些现有用法：`runtime/src/renderer/index.vue:57` 的 `const { meta, model, resetFields, submit } = controller`、`defineExpose` 里约 30 处 `controller.xxx` 裸引用、`controller.ts:1154-1181` 的 `getErrors: validation.getErrors` / `getMeta: meta.getMeta` 子服务方法别名。

**项目已有的（自洽的）类/闭包分工规则**——已用类：错误类型（`ConfigFormError` / `TransactionError` / `ConfigFormFlowInterpreterError` 等，需要 `instanceof` + `extends Error`）、需要 `implements` 替换的适配器与存储（`MemoryProjectRepository` / `IndexedDBProjectRepository` / `IndexedDBProjectRecoveryDraftStore`）、`class ValueScopeStore implements ConfigFormValueScopeStore`（core，私有类 + `createConfigFormValueScopeStore` 工厂包装）、`class ConfigFormFlowInterpreter`。用工厂闭包：会被解构/裸引用传递的 API 表面、需惰性循环装配的服务图、纯 reducer/转换。

其他不该改的理由：`validationService` / `metaService` / `scopeService` 是 `let ... | undefined` + `requireScopeService()` 的惰性循环装配，类里只能退化成 `private x!` 或 setter 注入；`controller.ts:96-131` 构造期有严格顺序的副作用序列（resolve schema → 建 scope store → 派生 values → 跑 reaction → 回写 host model → 建 observer）；闭包的私有变量运行时真不可达（强于 `private`）；`model/__tests__/production-performance.test.ts` 的预算是「2000 节点事务 p95 < 16ms」，与原型方法共享/实例数量无关，类唯一的技术优势不在这条计分板上；`tsconfig.base.json` 是 `useDefineForClassFields: false` + `experimentalDecorators: true`，全面类化会把局部约定升级为全局约束。

`ConfigFormController` 是纯结构接口（成员全是函数类型属性），`createConfigFormController(options): ConfigFormController<TValues>` 已用显式返回类型获得 `implements` 同等的表面约束——类在这点上没有额外收益。

**真正该做的**：拆 `headless/src/services/controller.ts`（有效代码 1186 行）。该文件是残留的 composition root，已有 8 个 `controller-*` 子服务但内部仍留着 flat（无 scope）回退路径 + row mutation 包装 + 生命周期重入。建议抽出 `controller-flat-fallback.ts`、`controller-row-mutations.ts`、`controller-lifecycle.ts`，把 controller.ts 压到 300–400 行。

**改主意的触发条件**：需要 `controller instanceof X` 做运行时判别（如 devtools 探测实例）、或出现需要共享行为的多个 controller 变体时，再考虑类。
